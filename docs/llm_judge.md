# Оценка ответов моделью-судьёй

Судья: `Qwen/Qwen2.5-7B-Instruct`, ревизия `a09a35458c702b33eeacc393d103063234e8bc28`, 4-bit NF4 с double quantization и float16. Модель и токенизатор загружаются с одной закреплённой ревизией. Промпт и рубрика: `configs/judge_prompt.txt`, `configs/judge.json`. Оплачиваемые API не используются.

Вход — 30 сохранённых ответов из `results/baseline/baseline_answers.jsonl`. Конфигурация исходного прогона, вопросы и сами ответы проверяются существующим валидатором и читаются без изменения. Базовая 3B-модель заново не генерирует ответы. Лимит **512** относится к исходным ответам; судье выделено **768** новых токенов для JSON с объяснениями.

Статус реализации: CPU-проверки выполнены, GPU-инференс в этой среде не запускался. Реальных оценок и итоговых численных метрик пока нет. Они появятся в скачанном архиве после запуска на T4. Значения в unit-тестах — только тестовые фикстуры, не результаты модели.

Журнал проверок: [judge_validation.txt](judge_validation.txt). Проверены 44 CPU-теста, синтаксис Python и notebook, CLI, экспорт на временных фикстурах и контрольные суммы исходного baseline. Установка зависимостей и инференс 7B на T4 пока не проверены.

## Запуск в Colab T4

1. Откройте [notebooks/judge_colab.ipynb](../notebooks/judge_colab.ipynb) в Google Colab. Выберите GPU T4. Лучше использовать отдельную сессию от обучения или генерации baseline.
2. Проверьте `REPO_URL`, ветку `REPO_REF` и запустите ячейки по порядку. Существующая папка `/content/PlantAdvisorJudge` автоматически не обновляется; в ней должна быть актуальная копия проекта. После установки зависимостей перезапустите Python, если этого попросит Colab.
3. Выполните проверку baseline и CPU-тесты. Затем запустите три пробные оценки: `q01` (care), `q02` и `q26` (diagnosis). В notebook появится таблица оценок и объяснений.
4. В `q02` ответ предлагает повысить влажность, когда воздух «слишком влажный». Это контрольный пример ошибки содержания. Проверка `known_error_penalized` показывает, снизил ли судья хотя бы одну из двух оценок: Factual Correctness или Actionability. Объяснение нужно прочитать вручную: само снижение оценки не доказывает, что судья заметил именно эту ошибку. Эта заметка и ожидаемая ошибка судье не передаются.
5. Проверьте числовые оценки, причины снижения, `null` у Diagnostic Reasoning для care и конкретное объяснение потенциального вреда при `critical_error=true`. Убедитесь, что судья не оценивает оформление. Если судья пропускает явную ошибку, сначала разберите причину; не подгоняйте рубрику под итоговые метрики теста.
6. Включите `RUN_FULL_JUDGE=True` в первой ячейке, повторите её и ячейку полного запуска. Без трёх валидных sanity-оценок код не начнёт оценивать все 30 ответов. Успешная JSON-проверка не заменяет ручную проверку содержания трёх оценок.
7. Посмотрите таблицы `scores.csv`, `metrics.csv` и `coverage`. `complete=true` означает, что получены 30 валидных оценок. Скачайте ZIP: установите `DOWNLOAD_RESULTS=True` и выполните последнюю ячейку до завершения сессии.

При исходных переключателях «Выполнить всё» оценивает только три примера. Sanity и полный тест хранятся раздельно; в полном запуске все 30 ответов оцениваются независимо, в зафиксированном случайном порядке. Модель запускается в отдельном процессе, освобождающем GPU после завершения команды.

## CLI

При `invalid_json` у всех пробных записей не включайте полный запуск. Выполните ячейку «Диагностика JSON»: она покажет `parse_error`, `finish_reason`, число токенов и исходный текст каждой попытки без нового инференса. Пустые баллы означают отсутствие валидной оценки. По одной таблице нельзя установить, обрезался ли JSON по лимиту или модель нарушила схему. Отрицательный флаг известной ошибки при невалидной оценке также не является выводом о качестве судьи. Сохраните архив неудачного запуска для анализа; обычный повторный запуск пропустит уже записанные невалидные ответы.

Из корня репозитория в Colab:

```bash
python -m pip install -r requirements-judge.txt
python -m pip install --no-build-isolation -e .
python -m plant_advisor audit
python -m plant_advisor judge
python -m plant_advisor judge --full
```

Путь к результатам выводится в консоль. Для программного чтения добавьте `--result-file outputs/judge_last_run.json`: файл содержит сводку и `run_dir`. Повторный вызов продолжит согласованный checkpoint, пропуская сохранённые записи. Невалидные JSON не переоцениваются при обычном продолжении: для отдельной повторной попытки с тем же протоколом можно использовать новый `--output-root`, сохранив предыдущий запуск для анализа.

Пересчитать таблицы из уже полученных оценок можно на CPU:

```bash
python -m plant_advisor judge-export --run-dir outputs/judge/<run_id> --mode full
python -m plant_advisor judge-export --run-dir outputs/judge/<run_id> --mode sanity
```

## Артефакты

```text
outputs/judge/<run_id>/
  protocol.json          # полная рубрика, промпт, ревизия, NF4, генерация, JSON-поля
  input_manifest.json    # исходные вопросы/ответы и отпечаток их конфигурации
  evaluation_config.json # хеши протокола, входа, runtime, порядок оценивания
  runtime.json           # версии, GPU/CUDA, chat template, GenerationConfig, хеши кода
  pip_freeze.txt
  sanity/
    judgments.jsonl
    scores.csv
    metrics.csv
    summary.json
  full/
    judgments.jsonl
    scores.csv
    metrics.csv
    summary.json
```

JSONL содержит исходные вопрос/ответ, структурированную оценку, статус, время и все исходные ответы судьи, включая неудачные попытки. Для каждой попытки записываются число входных/выходных токенов и причина завершения (`eos` или `length`). Один ответ судьи должен быть JSON-объектом с восемью полями:

- `factual_correctness`, `actionability`: целые числа 1–5.
- `diagnostic_reasoning`: целое 1–5 для diagnosis, `null` для care.
- `factual_correctness_explanation`, `actionability_explanation`, `diagnostic_reasoning_explanation`: непустые объяснения.
- `critical_error`: boolean; `critical_error_explanation`: основание флага или пояснение отсутствия выявленного вредного совета.

Строки вместо чисел, boolean вместо оценки, значения вне диапазона, повторные или лишние ключи отклоняются. Разрешён один JSON-блок в Markdown-ограждении, но не поясняющий текст вокруг него. Невалидный JSON вызывает максимум одну корректирующую попытку с сохранением исходного ответа. Если повторная попытка тоже невалидна, запись получает `status=invalid_json`, `evaluation=null`. CUDA-ошибки и превышение входного лимита останавливают выполнение; текст ответа незаметно не обрезается.

## Интерпретация метрик

`metrics.csv` содержит строки care, diagnosis и ALL. Для каждого критерия записаны среднее и число валидных оценок. Diagnostic Reasoning в строке ALL усредняется только по diagnosis; `null` не превращается в ноль. Отдельно записываются количество и доля `critical_error`.

При полном успехе ожидаются 30 оценок Factual Correctness, 30 Actionability и 15 Diagnostic Reasoning. Доля критических ошибок считается **среди валидных оценок**, а `summary.json` отдельно показывает число попыток, невалидных JSON, покрытие `valid/expected_count` и `complete`. При неполном покрытии метрики нельзя выдавать за оценку всех 30 ответов. `complete` означает техническую полноту, а не доказанное качество работы судьи.

Судья получает только `task`, `question`, `answer`, без названия оцениваемой модели, run_id или форматных баллов. Рубрика запрещает принимать оформление за правильность. Наблюдаемые оценки остаются суждением модели; Qwen 7B и baseline принадлежат одному семейству и могут разделять ошибки. Содержательную адекватность следует проверять вручную на примерах, особенно на вредных советах и спорной диагностике.

## Сохранение протокола для сравнения после SFT

Архив baseline-оценки нужно сохранить целиком. Для последующего оценивания нового набора ответов используется тот же код с `--source-dir` и `--reference-run`:

```bash
python -m plant_advisor judge --source-dir outputs/runs/<new_answers_run> \
  --reference-run outputs/judge/<baseline_judge_run>
python -m plant_advisor judge --source-dir outputs/runs/<new_answers_run> \
  --reference-run outputs/judge/<baseline_judge_run> --full
```

Этот режим читает сохранённый `protocol.json` и требует того же теста и runtime: версии ML-библиотек, Python/CUDA/GPU, ревизии модели и токенизатора, chat template, полная конфигурация генерации и реализация судьи должны совпадать. Изменение оцениваемых ответов создаст отдельный run_id. При изменении окружения сравнение не будет молча продолжено. Загрузка LoRA и обучение в текущую реализацию не входят.

## Источники реализации

Модель и закреплённая ревизия проверены по [официальной карточке Qwen](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct) и [метаданным репозитория](https://huggingface.co/api/models/Qwen/Qwen2.5-7B-Instruct). Загрузка NF4 использует [официальный интерфейс Transformers / bitsandbytes](https://huggingface.co/docs/transformers/v4.57.1/quantization/bitsandbytes). Совместимость конкретного установленного окружения с T4 требует реального пробного запуска; документация не заменяет GPU-проверку.
